# 수동 CI/CD 배포 가이드

이 문서는 GitHub Actions에서 `Sync and Deploy` 워크플로를 수동으로 실행해 GitHub Pages를 최신화하는 절차를 설명한다. 수동 실행은 저장소 메타데이터를 즉시 갱신하거나, 이전 배포를 다시 실행해야 할 때 사용한다.

## 실행 전 확인

- 대상 저장소의 GitHub Actions 워크플로를 실행할 권한이 있어야 한다.
- 기본 브랜치 `main`을 선택한다.
- 동기화와 배포는 워크플로에 설정된 `GITHUB_TOKEN`과 `GITHUB_OWNER`를 사용한다. 토큰이나 환경 변수 값을 화면·로그·문서에 복사하지 않는다.
- 다른 배포가 진행 중이면 완료될 때까지 기다린다. `pages` 동시성 그룹은 진행 중인 배포를 취소하지 않고 순서대로 처리한다.

## 수동 배포 실행

1. GitHub 저장소에서 **Actions** 탭을 연다.
2. 왼쪽 워크플로 목록에서 **Sync and Deploy**를 선택한다.
3. **Run workflow**를 누르고 브랜치를 `main`으로 지정한다.
4. **Run workflow**를 다시 눌러 실행한다.
5. 새로 생성된 실행 항목을 열어 `build`와 `deploy` 작업의 상태를 확인한다.

## 정상 완료 기준

`build` 작업은 아래 순서가 모두 성공해야 한다.

1. 의존성 설치(`npm ci`)
2. 공개 저장소 메타데이터 동기화(`npm run sync`)
3. 테스트 실행(`npm test`)
4. 프로덕션 빌드(`npm run build`)
5. `dist` Pages artifact 업로드

`build`가 성공하면 `deploy` 작업이 GitHub Pages 환경에 artifact를 배포한다. `deploy` 작업이 성공하고 환경 URL이 표시되면 배포가 완료된 것이다.

## 배포 후 확인

- `deploy` 작업의 GitHub Pages 환경 URL을 열어 최신 화면이 제공되는지 확인한다.
- 저장소 목록, 긴 저장소명, README가 없는 항목 등 주요 화면이 정상적으로 표시되는지 확인한다.
- 필요한 경우 브라우저 캐시를 새로고침한 뒤 다시 확인한다.

## 실패 시 확인 순서

| 실패 단계 | 먼저 확인할 내용 | 대응 |
| --- | --- | --- |
| `Sync public repositories` | API 접근 오류, 대상 저장소 공개 상태, 설정된 소유자 | 오류 로그에서 실패한 요청만 확인하고 권한·대상 설정을 점검한 뒤 다시 실행한다. |
| `Test` 또는 `Build` | 테스트·빌드 오류 메시지 | 로컬에서 동일 명령을 재현하고 수정은 별도 PR로 진행한다. |
| artifact 업로드 | `dist` 생성 여부 | 빌드 로그를 확인해 산출물 경로 또는 빌드 실패를 해결한 뒤 다시 실행한다. |
| `Deploy to GitHub Pages` | GitHub Pages 환경 및 배포 로그 | Pages 설정과 배포 로그를 확인한 뒤 다시 실행한다. |

실패한 실행의 로그에는 인증 정보나 토큰 값을 공유하지 않는다. 워크플로 설정, 권한, 환경 변수, artifact 경로를 변경해야 하는 경우에는 `docs/operations/ci-cd-rules.md`와 관련 워크플로를 같은 변경에서 함께 갱신한다.

## 자동 실행과의 관계

`Sync and Deploy`는 `main` 푸시와 매일 09:17(Asia/Seoul)에도 실행된다. 즉시 메타데이터를 갱신하거나 실패한 배포를 재시도할 필요가 있을 때만 이 수동 절차를 사용한다.
