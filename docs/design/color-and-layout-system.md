# Repolio 색상 및 레이아웃 시스템

> 이 문서는 Repolio의 색상 역할, 토큰 명명, 화면 배치, 컴포넌트별 적용 기준을 정의한다. 실제 값의 원본은 `src/styles/tokens.css`이며, 새 UI와 토큰 변경은 이 문서와 `design-rules.md`를 함께 따른다.

## 1. 목적과 적용 범위

- 저장소 탐색 화면에서 정보의 위계와 비교 가능성을 유지한다.
- 색상값을 컴포넌트마다 복제하지 않고, 역할별 토큰을 통해 라이트·다크 테마를 함께 관리한다.
- 상태를 알리는 색상과 사람이 관리하는 저장소 분류 색상을 분리한다.
- 페이지, 필터, 저장소 카드, README 미리보기의 배치 원칙을 한곳에서 확인할 수 있게 한다.

이 문서는 USWDS의 역할별 색상 체계, Radix Colors의 단계형 라이트·다크 팔레트, Ant Design의 전역 토큰, Primer Primitives의 기본값·기능 토큰·컴포넌트 토큰 분리를 참고한다. 외부 시스템의 명칭이나 값을 그대로 복사하지 않으며, Repolio의 작은 토큰 체계에 필요한 원칙만 적용한다.

## 2. 토큰 계층과 명명 규칙

### 2.1 현재 전역 역할 토큰

`src/styles/tokens.css`의 전역 토큰은 모든 일반 UI의 기본값이다.

| 역할 | 토큰 | 사용 위치 |
| --- | --- | --- |
| 페이지 배경 | `--canvas` | 페이지와 README 배경 |
| 기본 표면 | `--canvas-subtle` | 카드, 입력, 버튼 표면 |
| 구분된 내부 표면 | `--canvas-inset` | 코드, 언어 막대의 빈 영역 |
| 핵심/본문/보조 텍스트 | `--fg`, `--fg-muted`, `--fg-subtle` | 제목, 설명, 메타데이터 |
| 일반/약한 경계 | `--border`, `--border-muted` | 제어 요소와 카드 구분선 |
| 기본 강조 | `--accent`, `--accent-emphasis`, `--accent-muted` | 링크, 주요 조작, 일반 그룹 칩 |
| 상태 | `--success`, `--success-muted`, `--danger-muted` | Public, 성공, 오류/위험 알림 |
| 키보드 포커스 | `--focus` | `:focus-visible` 윤곽선 또는 그림자 |

일반 컴포넌트는 위 토큰을 먼저 사용한다. 언어 비율 막대처럼 외부 데이터의 고유 색을 전달해야 하는 경우만 예외로 직접 색상값을 허용한다.

### 2.2 새 토큰을 추가하는 순서

새 역할이 기존 토큰으로 표현되지 않을 때만 다음 순서로 추가한다.

1. `tokens.css`의 라이트·다크 테마 양쪽에 값을 정의한다.
2. 역할과 사용 범위를 이 문서에 기록한다.
3. 컴포넌트는 새 토큰을 참조하고 HEX·RGB 값을 직접 넣지 않는다.
4. 대비, 키보드 포커스, 작은 화면, 긴 한글 텍스트 상태를 확인한다.

전역 토큰을 추가하기 전에 특정 컴포넌트에만 필요한 값인지 판단한다. 특정 컴포넌트에서만 필요한 경우에도 값의 원본은 토큰에 두고, 컴포넌트 CSS에서는 역할별 변수로 별칭을 만든다.

## 3. 색상 사용 규칙

### 3.1 상태 색상

상태색은 시스템 상태를 전달할 때만 사용한다.

| 상태 | 허용된 예 | 금지된 예 |
| --- | --- | --- |
| 성공 | Public, 동기화 성공, 완료 | 프론트엔드 카테고리 |
| 오류/위험 | 오류 메시지, 실패, 삭제 위험 | API·연동 카테고리 |
| 경고 | 사용자 주의가 필요한 알림 | 일반 저장소 분류 |
| 정보 | 안내 메시지, 비파괴적 상태 | 서비스 도메인 카테고리 |

상태는 색상만으로 전달하지 않는다. 상태명, 아이콘, 또는 오류 설명을 함께 제공한다.

### 3.2 저장소 분류 색상

상위 그룹은 상태가 아닌 분류다. 그룹에 독립 색상을 도입할 경우 상태 토큰을 재사용하지 않고 다음 이름 체계를 사용한다.

```css
--category-<분류-id>-fg
--category-<분류-id>-border
--category-<분류-id>-muted
```

예를 들어 `frontend`, `api-integration`, `service-domain`은 각각 자신의 `fg`, `border`, `muted` 세 토큰을 가진다. `fg`는 상위 칩과 텍스트, `border`는 하위 영역의 경계, `muted`는 은은한 하위 영역 배경에 사용한다.

분류 색상을 추가하지 않은 동안에는 모든 그룹이 기존 `--accent` 계열을 사용한다. 이 경우에도 상위 그룹명, 세부 그룹 수, 하위 그룹 컨테이너를 함께 보여 관계를 구조적으로 전달한다.

### 3.3 명도 단계의 역할

한 색상군은 단일 색으로 끝내지 않는다. 라이트·다크 테마별로 다음 역할을 분리한다.

| 역할 | 용도 |
| --- | --- |
| 은은한 배경 | 선택 전 하위 그룹 컨테이너, 보조 강조 배경 |
| 경계 | 칩 테두리, 컨테이너 왼쪽 경계 또는 구분선 |
| 읽을 수 있는 전경 | 칩 레이블, 개수, 상호작용 텍스트 |
| 강조 전경 | hover, 현재 선택, 핵심 조작 |

각 역할은 해당 테마의 표면과 충분한 대비를 확보해야 한다. 라이트 값에 어울리는 어두운 전경을 다크 테마에 그대로 재사용하지 않는다.

## 4. 화면 배치 규칙

### 4.1 페이지와 목록

- 페이지 콘텐츠는 `.page-shell` 안에 두고 `--page-width`를 넘기지 않는다.
- 저장소 목록은 1121px 이상 3열, 768px부터 1120px까지 2열, 767px 이하 1열을 사용한다.
- 카드 높이를 인위적으로 맞추지 않는다. 설명의 최소 높이와 README 미리보기의 제한 높이만 유지한다.
- 새 breakpoint는 기존 1120px·767px 기준으로 해결할 수 없는 경우에만 추가한다.

### 4.2 저장소 카드 정보 위계

카드 안의 정보 순서는 아래를 고정한다.

1. 상태 배지
2. 저장소명과 외부 GitHub 열기 버튼
3. 설명
4. 그룹
5. 별 수, 포크 수, 브랜치 수, 마지막 수정일
6. 언어 비율
7. README 미리보기

새 메타데이터를 추가하려면 GitHub 동기화 범위, 카드의 읽기 우선순위, 작은 화면 줄바꿈 영향을 함께 검토한다.

## 5. 컴포넌트별 적용 기준

### 5.1 배지와 외부 링크 버튼

- `Public`, `Fork`, `Archived`는 기존 badge 패턴을 사용한다.
- 아이콘만 있는 GitHub 열기 버튼은 `icon-button` 패턴과 구체적인 `aria-label`을 가진다.
- hover는 색상·테두리 변경처럼 가벼운 피드백만 사용하고, 레이아웃 이동이나 확대는 사용하지 않는다.

### 5.2 상위 그룹과 하위 그룹

- 상위 그룹 칩을 클릭하면 같은 그룹을 가진 저장소를 필터링한다.
- 세부 그룹 열기/닫기는 상위 그룹별로 독립된 제어 요소여야 한다. 하나의 공통 목록에 서로 다른 상위 그룹의 하위 칩을 섞지 않는다.
- 펼친 상태에서는 `상위 그룹 칩 → 세부 그룹 수 → 해당 상위 그룹의 하위 컨테이너` 순서를 유지한다.
- 하위 컨테이너는 상위 그룹과 같은 토큰 묶음의 전경·경계·은은한 배경을 사용한다.
- 색상 외에도 상위 그룹명, 세부 그룹 수, 컨테이너 경계로 소속을 확인할 수 있어야 한다.
- 토글은 실제 상태와 일치하는 `aria-expanded`를 제공하고 키보드로 조작할 수 있어야 한다.

### 5.3 메타데이터·언어·README

- 메타데이터는 보조 정보이므로 `--fg-muted`를 사용하며 아이콘과 수치를 함께 표시한다.
- 언어 막대의 색은 언어 데이터 색상이며, 막대 아래에 언어명과 비율을 텍스트로 함께 표시한다.
- README는 카드 내부의 보조 영역이다. 기본 상태는 제한 높이와 페이드를 유지하고, 확장·접기 시 해당 README의 맨 위가 보이도록 스크롤 위치를 초기화한다.

## 6. 테마와 접근성 검증

변경 전 다음을 확인한다.

- [ ] 라이트·다크 테마에서 표면, 텍스트, 경계, 그룹 전경의 대비가 충분한가?
- [ ] 색상 없이도 상태와 상위·하위 그룹 관계를 이해할 수 있는가?
- [ ] 모든 버튼과 토글에 접근 가능한 이름, `:focus-visible`, 실제 상태와 맞는 ARIA 속성이 있는가?
- [ ] `prefers-reduced-motion`을 존중하는가?
- [ ] 긴 저장소명·한글 설명·URL·README 없음·하위 그룹 없음 상태가 유지되는가?
- [ ] 1120px, 767px, 320px에서 카드의 정보 순서와 줄바꿈이 유지되는가?
